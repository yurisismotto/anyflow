## 0. What this document is

It records the promotion of the certified release candidate to a published,
signed, publicly verifiable **v1.0.0**, and the evidence for every claim in
that sentence.

It is **not** a re-certification. The RC was certified on a tree whose product
code is byte-identical to this one; §3 makes that argument and §3.4 is explicit
about the one thing that genuinely changed in the shipped executables and why.

### 2.1 The gate this tripped, and why it was sharpened rather than weakened

The first push turned **Packaging · checks** red. `release-signing-tests.sh`
forbids any tracked `.gpg`/`.asc`/`.key`/`.pem`, and §2 commits one.

The gate was right to fire and was **not** weakened; the key was **not**
renamed to slip past it. As written, the check proved nothing about *content*:
it matched an extension, so a secret key committed as `notes.txt` passed it
and a public key named `.asc` failed it — the same *"a header is not a key"*
mistake SIGN-NEG-06 already carries a long comment about, in its name-shaped
form.

Exactly one path is now exempt from the name rule, and that path is **opened**:

* every other key-shaped tracked file is rejected as before;
* the published key **must be** committed — a documented URL that 404s is a
  recipe with no first step;
* it must carry no PGP/OPENSSH/ENCRYPTED/RSA/EC/DSA private armour;
* it must be an armoured **public** key block;
* importing it must yield **zero** secret key files;
* its primary fingerprint must equal the one `README.md` publishes — **read out
  of `README.md`** rather than repeated as a literal, so the key and the
  document a user trusts cannot drift apart silently.

The private-armour detector proves itself first, on a **real** exported secret
key (the ephemeral per-run test identity, never a production one), and an empty
`git ls-files` is a precondition failure rather than a pass.

Each rejection was **measured** against a throwaway clone, not asserted:

| Failure mode | Result |
| --- | :-: |
| a second key-shaped file committed | rejected, naming the file |
| a real private key at the allowed path | rejected on armour, and on not being a public block |
| a **different** public key at that path | rejected on fingerprint, printing both |
| the published key deleted | rejected |

Suite: **54 passed / 1 failed → 61 passed / 0 failed**; the eight assertions
above replace the one that existed.

### 3.4 The executables differ, and exactly why

**They must.** Rust v0 symbol mangling embeds a per-crate disambiguator derived
from `-C metadata`, and the crate **version** is an input to it. Bumping the
version changes the disambiguator of every OmniBridge crate, which changes
every mangled symbol naming one, which perturbs codegen-unit partitioning and
therefore byte layout. Byte equality is neither achievable nor expected, and a
delta that demanded it would block a release over arithmetic.

**The control that makes this an explanation rather than a story:**

| Crate | RC disambiguator | GA disambiguator | |
| --- | --- | --- | :-: |
| `omnibridge` | `jOBlT33Dtr` | `k8aYyG2qzFn` | **moved** |
| `omnibridge_control` | `c9QbEOQSS8W` | `bbCsA2QvPo5` | **moved** |
| `omnibridge_linux` | `crevgFPhyzU` | `icYsDKZakfh` | **moved** |
| **35 third-party crates** (`zbus`, `tokio`, `alloc`, …) | — | — | **unchanged** |

Had the build environment been the cause, the third-party hashes would have
moved too. They did not. The toolchain is identical in both builds: `rustc
1.98.1`, the same GCC.

What was measured on the executables:

| Measurement | Result |
| --- | --- |
| `.text` **size** | identical on **5 of 12** binaries; the largest difference is −2 176 bytes of ~9 MB (**−243 ppm**) |
| other section sizes | ≤ 0.15 % (`.strtab` +430 B on the CLI — a longer disambiguator string × many symbols) |
| symbol **count**, Fedora CLI | 3 238 → 3 238 |
| symbol **names**, Fedora CLI | **exactly identical** once the disambiguator and its backreferences are normalised |
| symbol count, Fedora daemon | 18 657 → 18 657; **3** residual symbols, all `core::ptr::drop_glue` |
| Fedora GUI | 4 373 → 4 371; residuals are `drop_glue` and monomorphised `alloc::raw_vec` helpers whose owning codegen unit moved |
| version bytes, all 12 binaries | RC carries `0.1.0` and no `1.0.0`; GA carries `1.0.0` and **no `0.1.0`** |

v0 backreferences (`B2m_`) are byte offsets into the mangled name, so they
shift when the disambiguator's **length** changes — `jOBlT33Dtr` is 10
characters and `k8aYyG2qzFn` is 11. Normalising the hash without normalising
the backreferences reports identical functions as different; that was measured
and corrected before any conclusion was drawn.

**NOT EXECUTED — recorded, not passed.** Symbol comparison could not run on the
**nine `.deb` binaries**: `dh_strip` removes `.symtab`, so there is nothing to
compare. Their evidence is section sizes, the version bytes, the identical
package manifests, and §3.3 — not a symbol claim.

### 8.1 A publication hazard, found and handled

A GitHub release page is a **flat namespace**. Three distributions build
`omnibridge_1.0.0-1_amd64.deb` and three build `omnibridge-gui_1.0.0-1_amd64.deb`,
so a flat upload of the 14 artifacts would have published **10 distinct names**
and silently dropped four packages — the same *"ships less than it built"*
failure the workflow's own count guard exists to prevent, reappearing one step
later.

`SHA256SUMS` is signed and records **per-distribution paths**, and re-signing
was not an option, so the release publishes both forms:

| Asset | Purpose |
| --- | --- |
| `omnibridge-1.0.0-linux-x86_64.tar.gz` | every artifact **in its signed layout**, with `SHA256SUMS` and `SHA256SUMS.asc` — this is what `verify-release.sh` checks |
| 14 flat packages, `.deb`s prefixed `ubuntu2404-`, `ubuntu2604-`, `debian13-` | the same bytes, individually downloadable, nothing dropped |
| `SHA256SUMS`, `SHA256SUMS.asc` | inspectable without an 80 MB download |
| `omnibridge-release-pubkey.asc` | the public signing key |

Reconciled both ways before publishing: **all 14** flat assets' digests appear
in the signed manifest, and **all 14** manifest entries have a flat published
counterpart.

### 8.2 What was not uploaded

No private key in any form, no encrypted backup, no revocation certificate, no
`GNUPGHOME`/trustdb/keybox, no internal logs, no VM images, no raw test state.
Scanned with a detector proved on a planted key; 0 hits.

## 16. Tag policy note

`v1.0.0` is **annotated and not OpenPGP-signed**. The repository had **no tags
at all** before it and no signed-tag policy. Signing it would have introduced a
second trust mechanism nobody had decided on, alongside the release signature
that *is* the decided one — so it was not done, and the tag message says so. If
the project later adopts signed tags, that is a deliberate decision to take on
its own terms.
